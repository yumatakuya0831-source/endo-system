# システム開発ドキュメント一式(sdlc-docs)

要件定義・設計・テスト・進捗管理の4文書と、それらを貫く共通ルール・AIエージェント向け作業規範を、どんなシステムにも使い回せる汎用テンプレートとして提供する。`assets/` 配下の原本を保ち、出力先へコピーしてからプロジェクト固有の内容を記入する。配置先に応じてファイル参照だけを調整してよい。

## 6つの資産とその役割

| ファイル | 種別 | 目的 |
| --- | --- | --- |
| `assets/development-rules.md` | 規範文書 | 技術スタック・業種によらない共通ルール。原則、役割分担、ID規則、状態区分、各工程の必須項目と完了ゲート、品質保証・リリース判定基準を定める。他の全文書はこれに従う。 |
| `assets/AGENTS.md` | AIエージェント向け作業規範 | リポジトリで作業する人・AIエージェントが development-rules.md を規範として、作業開始前・作業中・作業完了時に何を確認し何を残すかを定める。優先順位(ユーザー指示 > 承認済み要件 > 承認済み設計 > development-rules.md > 本書 > その他参考資料)も規定。 |
| `assets/requirements-template.md` | 要件定義書 | 何を作るか・誰のためか・受け入れ条件を定義する |
| `assets/design-template.md` | システム設計書 | 要件をどう実現するかを構成・API・データ・非機能面で設計する |
| `assets/test-plan-report-template.md` | テスト計画・結果報告書 | 設計・要件を検証する計画とその実施結果を記録する |
| `assets/progress-template.md` | 開発進捗・決定・課題記録 | フェーズ状況・作業履歴・決定事項・課題・引き継ぎを継続的に記録する |

## 文書間のトレーサビリティ(最重要)

4つのドキュメントテンプレートは、development-rules.md 4.2で定めたID規則で繋がっている。新しいプロジェクトでテンプレートを埋める際は、このIDの一貫性を必ず守ること。

```
要件ID (FR-xxx) ──> 受入条件ID (AC-xxx) ──> 設計箇所/実装箇所 ──> テストID (T-xxx)
        │                    │                                      │
        └────────────────────┴──────────────────────────────────────┘
                  進捗記録の「作業履歴」「決定事項」で対象IDとして参照
```

- 要件定義書の「5. 機能要件」で発行した `FR-xxx` は、「9. 受入条件」で `AC-xxx` に紐づく。
- 設計書の「10. 要件対応表」は `要件ID` と `受入条件ID` の両方を引用し、どこで実現しているかを記録する。
- テスト報告書の「5. テストケースと結果」「9. トレーサビリティ」は `要件ID` `受入条件ID` `テストID` を突き合わせ、抜け漏れがないか確認する。
- 進捗記録の「作業履歴」「決定事項」「課題・リスク」の対象IDには、上記いずれかのID、または `ADR-xxx`(設計判断)・`BUG-xxx`(不具合)・`ISSUE-xxx`/`RISK-xxx`(課題・リスク)・`DEC-xxx`(決定事項)を用いる。

新規にIDを振るときは、既存文書内の最大番号+1を採番し、絶対に番号を再利用しない。廃止する場合も削除せず、廃止または置換先を記録する(development-rules.md 4.2)。

## 状態・判定の共通語彙(development-rules.mdに準拠)

テンプレート・ルール文書間で用語を揃えてあるので、埋める際もこれに従うこと。

- 文書全体の状態: `下書き / レビュー中 / 承認済み`(要件定義書・設計書)
- 項目単位の状態: `未着手 / 進行中 / レビュー待ち / 完了 / 保留`(機能要件、フェーズ状況など。development-rules.md 4.3)
- テスト結果: `合格 / 不合格 / 保留 / 未実施`(個別テストケース・総合判定とも共通。development-rules.md 8.2)

## 使い方(ワークフローの一般形)

対象システムの内容は問わない。ユーザーの発言から今どのフェーズかを判断し、対応するテンプレートを使う。

0. **リポジトリ/プロジェクトの土台として**: `assets/development-rules.md` と `assets/AGENTS.md` をコピーし、プロジェクトに配置する。配置場所を変える場合は、AGENTS.mdから規範文書への参照先を実際のパスに合わせる。
1. **プロジェクト開始時**: `assets/requirements-template.md` をコピーし、development-rules.md 5章の必須項目・書き方・完了ゲートに従ってヒアリング(背景・目的・利用者・業務フロー・機能要件・非機能要件・受入条件)しながら埋める。埋まっていない項目を空欄のまま進めない。
2. **要件が固まったら**: `assets/design-template.md` をコピーし、development-rules.md 6章に従って要件定義書のFR/ACを参照しながら設計する。ヘッダーの「入力要件版」には参照した要件定義書のバージョンを明記する。
3. **実装が一定進んだら/リリース判定が必要なら**: `assets/test-plan-report-template.md` をコピーし、development-rules.md 8〜9章に従って要件のAC単位でテストケースを起こす。ヘッダーの「対象要件版」「対象設計版」を明記する。
4. **プロジェクト進行中は常に**: `assets/progress-template.md` を1つ維持し、development-rules.md 12章の引き継ぎ形式も踏まえてフェーズ状況・作業履歴・決定事項・課題を都度追記する。「正本要件版/設計版/テスト版」には現在参照すべき各文書のバージョンを記入し、他文書を更新したら忘れずに同期する。
5. セッションを終える際・作業を引き継ぐ際は、進捗記録の「引き継ぎ」節を、development-rules.md 12章の項目(対象フェーズと対象ID、実施内容と変更ファイル、判断と理由、検証・結果・証拠、未実施・残課題・既知リスク、次に行うこと、入力・出力文書の版)を満たす形で更新するようユーザーに促す。
6. 指示が競合する、または文書間に矛盾がある場合は、AGENTS.md「優先順位」節の順序(ユーザーの最新の明示指示 > 承認済み要件 > 承認済み設計 > development-rules.md > AGENTS.md > その他参考資料)に従って判断し、判断根拠を進捗記録に残す。

## 埋める際の注意点

- 空欄のまま「後で埋める」項目は、進捗記録の「未実施・保留・残存リスク」または「未確定事項」に必ず転記し、宙に浮かせない。
- テンプレートの見出し番号・列構成は変更しない(他文書との対応関係が崩れるため)。プロジェクト固有で欄が足りない場合は、既存の表に列を足すのではなく、本文中に注記するか小見出しを追加する。
- 一度承認済みにした版を修正する場合は、要件定義書「12. 決定・変更履歴」または設計書「11. ADR・未解決事項・リスク」に変更理由を残す。
- development-rules.md 13章「テーラリング」の通り、小規模開発では文書を統合してよいが、必須情報と品質ゲートは省略しない。適用しない規則は理由と承認者を記録する。
- 6資産はセットで完結する。一部だけを渡されて作業する場合でも、他の資産の存在を前提にIDや版番号・状態語彙の整合を意識すること。
